# Campus Crypt status display (ELEGOO Mega 2560 kit, output only)

An optional bonus: an Arduino Mega 2560 from the ELEGOO Most Complete Starter Kit mirrors the game on real displays. **The game never needs it**, and the board is **output only**: the keyboard is the only control.

| Part | What it shows |
|---|---|
| **LCD1602** | Line 1: `HP 4/5` and a health bar. Line 2: `Kn2 F3/10   12:34` (Knowledge, floor of 10, real time). In the floor-1 Keeper fight: `* INBOX MIMIC *` / `F1/10 FIGHT` |
| **4-digit 7-segment** (bare 12-pin 5461AS) | `F  3` (the floor) while you play, a blinking `5:00` (the Mimic's deadline) during the Keeper fight, the clock on the title screen |
| **MAX7219 8x8 matrix** | Scrolling `CRYPT` on the title, a flickering torch while you play, a heart dodging in a box during the Keeper fight, a heartbeat when Health is low, a heart flash on a hit (Health or fight box), a burst on a right answer or level-up, stairs when you go down, a skull when you're overwhelmed |
| **DS1307 RTC** | Real time on the LCD and 7-segment |

With no game running, the LCD shows **`CAMPUS CRYPT` / `waiting...` + the time**, the 7-segment shows the clock and the matrix shows a small "radar" animation.

## Files

| File | What it is |
|---|---|
| `campus_crypt_display/campus_crypt_display.ino` | The Arduino sketch. Only uses **LiquidCrystal** and **Wire**, which come with the Arduino IDE |
| `WIRING.md` | Every wire, module by module, with resistor values, the 5461AS pinout and the wire count |
| `wiring_diagram.png` | The same wiring as a picture (generated by `tools/make_wiring_diagram.py`) |
| `DEMO.md` | Step-by-step on the Mac: upload, test, run the game, what to show, troubleshooting |
| `sim/crypt_sim.py` | A fake display for testing the game's serial link with no board (macOS/Linux, plain Python 3) |

Compiled with arduino-cli 1.6.0 / AVR core 1.8.8 for `arduino:avr:mega` (ATmega2560): **13,156 bytes of flash (5%)** and **912 bytes of RAM (11%)**, no warnings.

## Pin map (summary)

```
D2  MAX7219 DIN          D20  DS1307 SDA   (Mega I2C; A4/A5 are not I2C on a Mega)
D3  MAX7219 CLK          D21  DS1307 SCL
D4  MAX7219 CS           D22-D29  7-seg segments A,B,C,D,E,F,G,DP (1 kOhm each)
D7  LCD RS (4)           D30-D33  7-seg digits 1-4 (pins 12, 9, 8, 6)
D8  LCD E (6)            5V / GND  breadboard + / - rails
D9-D12  LCD D4-D7 (11-14)          D0/D1  USB serial (keep free)
```

Nothing is shared (the Uno build needed a shared D2/D3 bus and a 74HC595; the Mega has enough pins to drive the 7-segment directly). No pin is ever read as an input. **36 wires: 9 female-to-male Duponts + 27 male-to-male jumpers** (see `WIRING.md` for how to get to 33).

## How it works (non-blocking)

`loop()` never calls `delay()`. Each pass it:

1. reads any serial bytes and handles complete lines
2. refreshes the 7-segment display, one digit at a time, moving on every 2 ms (about 125 Hz per digit)
3. sends a `HB` heartbeat every 0.5 s while a game is talking to it (`HELLO:CRYPT` every 2 s while not)
4. reads the RTC twice a second
5. advances the matrix animation every 90 ms, sending only the rows that changed
6. updates the LCD from a "wanted text" buffer, at most 3 changed characters per pass (no `lcd.clear()`, no flicker)

## Serial protocol

**115200 baud**, 8N1. Every message is **one ASCII line ending in `\n`**; a `\r` is ignored.

### Game → board

| Line | Meaning |
|---|---|
| `S:hp,maxhp,lvl,floor,gold,kills,mode,disp,floors` | State, e.g. `S:4,5,2,3,4,1,P,F,10` |
| `E:HIT` | Health lost, a wrong Keeper answer, or a hit in the fight box: heart flash |
| `E:LVL` | A right answer, a safe choice or a beaten warden: burst |
| `E:STAIRS` | Down the stairs: stairs icon |
| `E:DIE` | Overwhelmed: skull |
| `E:MENU` | Back on the title screen: title scroll |
| `PING` | "Are you there?" The board answers `HELLO:CRYPT` |

In the `S:` line: `hp`/`maxhp` = Health (of 5), `lvl` = Knowledge, `floor`/`floors` = floor of 10, `gold` = Focus, `kills` = monsters and wardens defeated. `mode` is `M` (title), `P` (playing), `F` (the floor-1 Keeper fight), `X` (paused in the sound settings) or `D` (overwhelmed). `disp` picks the 4-digit display: `F` floor (what the game sends), `G` Focus or `K` kills. `disp` and `floors` are optional (defaults `F` and 10).

The game sends `S:` when something changes (at most 10 times a second) and otherwise every 0.5 s as a heartbeat. With no `S:` line for 3 s the board goes back to "waiting...".

### Board → game

| Line | Meaning |
|---|---|
| `HELLO:CRYPT` | At boot, every 2 s while no game is connected, and in reply to `PING` |
| `HB` | Heartbeat every 0.5 s while connected (the game drops a board that's silent for 2 s) |

The board sends **no joystick lines**. The game still understands Delve's old `J:x,y,btn` lines and `HELLO:DELVE`, so an old Uno controller would still work, but nothing waits for them: with no `J:` line the game's joystick input is simply zero.

### Connecting (game side)

1. The game looks for serial devices that look like an Arduino: `/dev/cu.usbmodem*`, `/dev/cu.usbserial*`, `/dev/cu.wchusbserial*`, `/dev/cu.SLAB_USBtoUART*` on macOS, `/dev/ttyACM*` / `/dev/ttyUSB*` on Linux.
2. It opens each at 115200 baud (this resets the board, ~1.5 s) and waits up to 3.5 s for `HELLO:CRYPT` (or `HB`), sending `PING` after 2 s.
3. All port I/O runs on a **background thread**, so the 60 Hz game loop never waits on USB.
4. If the port errors, disappears or goes silent for 2 s, the game drops it and keeps searching. Unplugging and replugging just works. A board that answers with something else is left alone for 20 s.
5. The title screen shows **Status display: Connected on /dev/…** while it's connected.

Force a port with `--hw-port /dev/cu.usbmodem1101` or `CAMPUS_CRYPT_HW_PORT`. Turn the scan off with `CAMPUS_CRYPT_HW=off`.

### Build options

* The serial support is the Cargo feature **`hardware`**, on by default. Without it: `cargo build --release --no-default-features --features ai`.
* It uses the `serialport` crate with default features **off**, so Linux builds don't need `libudev`.
* The **web (wasm) build** compiles a do-nothing stand-in.

## Live layout (LCD + matrix sketch)

`campus_crypt_lcd_matrix/campus_crypt_lcd_matrix.ino` (LCD1602 + MAX7219 only) can change what it shows **without a re-upload**. The layout is kept in the board's EEPROM, so it survives a reset; `LRESET` goes back to the built-in one.

| Line | Meaning |
|---|---|
| `LT:<screen><row>:<text>` | LCD line template, up to 32 chars. Screens: `W` waiting, `M` title, `P` playing, `F` Keeper fight, `X` paused, `D` overwhelmed. Rows `0`/`1` |
| `LM:<slot>:<ms>[:<hex16>[,<hex16>...]]` | Matrix picture, up to 4 frames of 16 hex digits (row 0 first, bit 7 = left), `ms` per frame. No frames = the built-in animation. Slots: the six screens plus `L` low health, `H` hit, `V` right answer / level-up, `S` stairs |
| `LB:<0-15>` | Matrix brightness |
| `LPREV:<screen or slot>` | Show a screen for 15 s, or play an event, to try a layout |
| `LSAVE` / `LRESET` | Keep the layout in EEPROM (answers `LOK:SAVED` when done) / go back to the built-in layout |

Each line answers `LOK` or `LERR`. Template fields: `{hp}` `{max}` `{kn}` `{fl}` `{fls}` `{focus}` `{kills}` `{dots}`, `{bar}` (health bar filling the line up to what follows it) and `{barN}` (N cells).

**Editing it:** the Crypt Display Studio page (`studio/display-studio.html`, shown through It) edits every screen with a live preview and sends the result. Underneath, `tools/live.sh` does the work:

```
hardware/tools/live.sh push layout.txt   # send + keep a layout (through the game if it is running)
hardware/tools/live.sh preview F         # show one screen on the board
hardware/tools/live.sh flash             # compile + upload the sketch (the game lets go of the port meanwhile)
hardware/tools/live.sh status
```

While the game runs it owns the USB port, so these go through it: `src/display_live.rs` watches `display_layout.txt`, `display_send.txt` and `upload.lock` in the settings folder (`~/Library/Application Support/campus-crypt/` on a Mac) and resends the layout whenever a board connects. With no game running, `live.sh` uses `target/*/crypt_display` (`cargo build --release --bin crypt_display`). Turning **Options > Arduino display** off also frees the port.

## Testing without a board

```bash
python3 hardware/sim/crypt_sim.py --duration 60 --strict     # terminal 1
cargo run --release -- --hw-port /tmp/crypt-sim-port          # terminal 2
```

The simulator makes a virtual serial port, does the handshake and heartbeat like the sketch, checks every line the game sends against the protocol, and prints what the LCD would show, then a summary (modes, floors, events, problems). `--replug 20` pretends to unplug for 3 s; `--no-hello` only answers `PING`.
